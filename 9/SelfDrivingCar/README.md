# Hack Self-Driving Car

This project is a self-driving car game for the nand2tetris Hack platform, written in Jack for ECEG 431 (Project 9). A multilayer perceptron (MLP) reads five distance sensors and controls the throttle, brake and steering of a car on a three-lane road with slower traffic. The program runs entirely on 16-bit integer arithmetic in the VM Emulator and uses no floating-point values. It was inspired by the Java project [Self-Driving-Car-Java](https://github.com/fynix-dev/Self-Driving-Car-Java) by fynix-dev. This is not a port of that project it just provided inspiration.

## Authorship

I wrote the Jack program: the simulation (car, traffic, collisions and sensors), the network, the drawing code and the game loop. The only Jack files I did not write by hand are `Weights.jack` and `Tables.jack`, which are generated by `export.py`.

Jack cannot train a network (see [Training](#training)), so I gave my simulation to Claude, Anthropic's AI model, and asked it to write a Python equivalent along with a training loop. **Claude wrote all of the Python in `tools/`.** That includes the Python copy of the simulator (`sim.py`), the trainer (`train.py`), the exporter that generates the two Jack files (`export.py`), the evaluator, the test runner and the screenshot script. The weights in the game were produced by that training loop and were not tuned by hand.

## Running the game

Compile the project folder with the Jack compiler, then load the folder into the VM Emulator. When the emulator offers its built-in OS, accept it. The OS `.vm` files should not be copied into this folder.

```bash
JackCompiler.sh .
```

Start the emulator with `VMEmulator.sh`, load the folder and run the program. The car drives itself from the first frame.

| Key | Action |
| --- | --- |
| M | Switch between AI and manual driving |
| Left / Right arrow | Steer (manual mode) |
| Down arrow | Brake (manual mode) |
| R | Restart with new traffic |
| Q | Quit |

In manual mode the car accelerates on its own. The right half of the screen shows the speed, the number of cars passed, the best score of the session, the frame count, and the current pedal and steering state.

## Network architecture

The network is an MLP with 10 inputs, two hidden layers of 12 and 8 neurons, and 4 outputs.

| Layer | Neurons | Computation |
| --- | --- | --- |
| Input | 10 | Sensor readings, each from 0 to 32 |
| Hidden 1 | 12 | Weighted sum, divide by 64, clamp to 0..32 |
| Hidden 2 | 8 | Weighted sum, divide by 64, clamp to 0..32 |
| Output | 4 | Weighted sum with no clamp; a value above 0 means the control is on |

The 272 parameters (12×(1+10) + 8×(1+12) + 4×(1+8)) are stored in one flat array. Each neuron's bias comes first, followed by its weights, and `Net.think` steps through the array with a single index. Jack has no multidimensional arrays, which is the reason for the flat layout.

### Inputs

`Sensor.jack` casts five rays from the car at -72°, -36°, 0°, +36° and +72° relative to its heading. Each ray produces two readings, the distance to the nearest traffic car and the distance to the road edge, which gives ten inputs. A reading is 0 when nothing lies within 150 pixels and rises to 32 at contact. The centre traffic ray is made of three parallel beams so that it is as wide as the car.

### Hidden layers

Each hidden neuron computes a weighted sum plus its bias, divides the result by 64 using integer division, and clamps it to the range 0 to 32, which makes it a clipped ReLU. Weights are integers from -63 to 63 and biases are limited to ±4096. The division by 64 brings the sums back to the scale of the inputs, and the clamp keeps the inputs of every layer in the same 0 to 32 range as the sensor readings. With these limits the largest sum each layer can produce is 24,256, 28,288 and 20,224, all below the 32,767 limit of a Jack integer for any weights inside the allowed range.

### Outputs

The four outputs have no activation function. Each output above zero turns on one control, and the four are packed into a control mask: 1 for accelerate, 2 for brake, 4 for steer right and 8 for steer left. The outputs are independent, so the car can accelerate and steer in the same frame. Steering centres itself, so on a frame with no steering input the heading moves one step back toward straight ahead.

The network runs on every third frame and its last decision is held for the frames in between. A forward pass takes 248 multiplications, which are expensive in Jack (see [Multiplication and division](#multiplication-and-division)).

## Simulation

`Sim.jack` contains the game rules. The car stays at y = 0 and never moves vertically, and the traffic moves past it. Four rows of traffic form a ring. A row that falls too far behind jumps to the front, a row that gets too far ahead wraps around to the back, and in both cases it receives a new random lane mask drawn from left, middle, right, or left and right together. Positions are measured in units (U) of 1/32 of a screen pixel, headings in half-degrees from 0 to 719, and speed in U per frame from 0 to 48. The traffic moves at a constant 31 U per frame.

The car is a rotated rectangle. A collision is detected when a corner of the car lies outside the road, when a corner of the car lies inside a traffic car, or when a corner of a traffic car lies inside the car. A traffic row counts as passed once it is entirely behind the car, and a row that wraps from the front to the back is not counted.

The screen is divided in half. `View.jack` draws the road on the left and `Hud.jack` prints the status text on the right.

## Training

Jack can run the trained network but cannot train it. There is no floating-point arithmetic, and the integer divisions and on/off outputs leave no usable gradient, so backpropagation does not apply. The remaining option is a search over many candidate networks, each driven through many frames of traffic. Measured on this machine, the VM Emulator running headless executes about 24 million VM steps per second and one drawn game frame costs about 0.4 million, which is roughly 60 frames per second. That is far too slow for the millions of frames a search needs. The Python simulation runs 2 million frames in under 3 seconds across the cores of this machine. It uses only the standard library because numpy is not installed here.

Claude wrote `tools/train.py` as a genetic algorithm. It starts from a population of random networks and drives each one for 3,000 frames on freshly generated traffic. A network's score is the distance it gains on the traffic stream, minus 4,000 if it crashes. The top eighth of the population are kept as elites. The next generation consists of the six best networks, the best network found so far, and children of the elites produced by crossover and mutation, with one child in ten receiving a larger mutation so that the search keeps exploring. The traffic layouts change every generation so that no network can memorise a particular road. The champion, which is the network written to disk, is selected on 96 fixed validation layouts, so a single lucky generation cannot win. All weights and biases stay within their legal ranges throughout, so every network the trainer produces can run in Jack without overflow.

```bash
python3 -O tools/train.py POP GENERATIONS SEEDS_PER_GEN tools/champion.json
python3 tools/export.py
```

`export.py` reads `champion.json` and writes `Weights.jack` and `Tables.jack`. The `-O` flag disables the overflow assertions, which roughly doubles training speed.

### Keeping Python and Jack identical

The trained weights are only useful if the Python simulation and the Jack program agree exactly. `sim.py` follows the same rules, order of operations and division points as the Jack code, and when it is run without `-O` it asserts that every product and sum fits in 16 bits. `run_tests.py` runs the Jack code on the VM Emulator and compares it with the Python values one by one. The comparison covers sensor readings, network outputs and complete frame-by-frame traces, and some of the traces use scripted drives that force a rear-end collision, a corner clip and a wall crash.

The `tests/` directory containing the Jack test drivers is not part of this copy of the project, so `run_tests.py` cannot be run until it is restored.

## Working within Jack's limits

Most of the design follows from the limits of Jack and the VM Emulator. The main ones, and how each was handled, are described below.

### 16-bit integers

An `int` in Jack is a signed 16-bit word with a range of -32,768 to 32,767, and there is no floating-point type. Every quantity in the game is therefore a whole number with a fixed scale: positions in 1/32 of a pixel, angles in half-degrees, and sine and cosine scaled by 128. The ranges were chosen by working backward from the overflow limit, which is where the weight range of ±63 and the 0 to 32 activations come from. `export.py` rejects any weight outside these ranges.

### Division

Jack's `/` truncates toward zero, while Python's `//` rounds down. The two differ on negative operands, so wherever a value can be negative `sim.py` writes the division as `int(a / b)`.

### Trigonometry and square roots

`Tables.jack` stores a quarter sine wave of 181 entries covering 0° to 90°. `Tables.init()` expands it at start-up into full 720-entry sine and cosine tables, with cosine taken as sine shifted by 90°. The sensors do not need a square root. Each ray direction is taken from the tables as a vector of length 128, and the distance to a wall is computed as `(offset × 128) / direction component`, which gives a length in pixels without normalising the vector.

### Random numbers

The Jack OS has no random number generator, so `Rng.jack` implements `seed = 171 × seed mod 30269`. Computed directly, 171 × seed overflows a 16-bit integer for any seed above 191, so the multiplication is carried out in Schrage's form, which splits it so that no intermediate value leaves 16 bits. The generator has the full period of 30,268, and a self-test in `sim.py` steps through every value to confirm it. Jack also has no `%` operator, so the modulo 6 that selects a lane mask is computed as `s - ((s / 6) * 6)`.

### Multiplication and division

Jack has no hardware multiply or divide, so `*` and `/` are OS routines. On the VM Emulator a multiplication costs about 270 VM steps and a division about 1,085. Besides running the network only every third frame, the program reduces this cost in several places. `Sensor.jack` skips empty traffic rows and rows outside sensor range before it does any geometry, `View.jack` erases only the parts of the screen that changed, and `Hud.jack` redraws text only when it changes, with the numbers refreshed every sixth frame.

### Program size and weight storage

The VM Emulator limits a program to 32,767 VM commands. The Jack classes in this project compile to 8,195 commands and the OS adds roughly 4,000, so there is plenty of headroom. Jack has no array literals and the program has no file to read, so the weights are stored in the code as 272 `let w[i] = n;` statements. At 2,321 VM commands, `Weights.jack` is the largest file in the project. The CPU Emulator is not an option, because with my Project 8 translator the OS alone produces 39,212 Hack instructions and the ROM holds 32,768. The game therefore runs on the VM Emulator.

### Heap

A string literal inside code that runs every frame allocates a new `String` each time and would eventually exhaust the heap. `Hud` therefore creates each string once in `init()`, and all other objects are allocated once at start-up.

### Drawing

The OS halts the program when something is drawn off screen. Every line therefore goes through `View.line`, which skips any line with an endpoint outside the road view, and rectangles are clipped before they are drawn.

### Language restrictions

Jack has no `for` loops, no `else if`, no `<=`, `>=` or `!=` operators, and no `&&` or `||`. The code uses `while` loops, nested `if` statements and `~(a = b)` instead. Because `&` and `|` do not short-circuit, both sides of a condition are always evaluated. Jack applies no operator precedence, so expressions are fully parenthesised, and negative constants are written in parentheses, as in `(-150)`.

## Results

The trained network was evaluated on 200 traffic layouts it had not seen, each run for 10,000 frames. It did not crash in any run, passed 41.7 cars per run on average, and gained 156,502 U on the traffic against a maximum possible gain of 160,000 U, about 98%.

```bash
python3 -O tools/evaluate.py tools/champion.json 200 10000
```

One limitation is that the traffic never places two cars side by side in neighbouring lanes. The trained network did not learn to handle that case, so the corresponding lane masks were removed from the game. The only two-car pattern in the game is one car in each outer lane.
